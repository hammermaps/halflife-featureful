# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Half-Life Featureful SDK — a fork/superset of the classic GoldSource Half-Life SDK (`dlls` = server game logic, `cl_dll` = client game logic) targeting both GoldSource and Xash3D FWGS engines, with extra monster/weapon/entity features and a data-driven (JSON) configuration layer on top of the original C++ entity system. It's a game DLL project (`server.dll`/`client.dll` equivalents), not an application — there is no "run" step other than loading the built libraries into a Half-Life-compatible engine.

## Build

Two parallel build systems exist: **CMake** (primary, used in CI) and **waf** (legacy, still supported).

### CMake

```bash
cmake -DCMAKE_BUILD_TYPE=Release -B build -S .
cmake --build build
```

Useful options (pass as `-D<NAME>=<VALUE>`, see `mod_options.txt` for the full list of mod-specific options):
- `BUILD_CLIENT` / `BUILD_SERVER` (default `ON`) — build only one side.
- `64BIT` — 32-bit build is the default on x86 platforms; most Half-Life engines expect 32-bit.
- `GOLDSOURCE_SUPPORT` — build a client lib compatible with original GoldSource (auto-detected per platform).
- `GAMEDIR` + `CMAKE_INSTALL_PREFIX` — set to install straight into a mod directory, then build with `--target install`.
- Custom mod options can be added to `mod_options.txt` as `NAME=VALUE # description` and are auto-registered as CMake options and `-D` compile definitions.

Outputs land as `hl.dll`/`client.dll` (Windows) or `.so` equivalents (Linux) under `build/dlls` and `build/cl_dll`.

### waf (legacy, requires Python 2.7+)

```bash
./waf configure -T release
./waf
```

### Platform notes
- Linux target is normally a 32-bit Steam Runtime build (see README for the podman/schroot/chroot recipes); a plain `cmake --build` on a modern distro also works but binaries may not be portable to old Steam runtimes.
- Android: open `android/` in Android Studio, or `cd android && ./gradlew assembleRelease`.
- Also supports Nintendo Switch (devkitPro) and PS Vita (VitaSDK) via both waf and CMake.

## Tests

Unit tests live in `tests/` and use GoogleTest, built as a **separate CMake project** (not part of the top-level `CMakeLists.txt` build):

```bash
cd tests
cmake -B build -S .
cmake --build build
./build/test
```

Requires `libgtest-dev` (or gtest discoverable by CMake) installed on the system. Tests compile a curated subset of `game_shared/`, `dlls/`, `cl_dll/`, and `public/` sources directly (see `tests/CMakeLists.txt`'s explicit source list) alongside the `tests/*_test.cpp` files — the game code isn't built as a library first. To run a single test binary filter, use gtest's own flag: `./build/test --gtest_filter=SuiteName.CaseName`.

When adding a new `dlls`/`cl_dll`/`game_shared` source file that a test needs, add it to the `add_executable(test ...)` source list in `tests/CMakeLists.txt` explicitly.

### Always run tests/binaries under gdb

Run the GoogleTest binary and any runtime smoke test (engine, dedicated server, graphical client) under `gdb` rather than directly, so a crash produces a full backtrace instead of a bare exit code:

```bash
gdb -q -batch -ex run -ex bt --args ./tests/build/test [--gtest_filter=...]
gdb -q -batch -ex run -ex bt --args ./xash3d -dedicated -game featureful +map <mapname> -log
```

For a long-running process that doesn't exit on its own (dedicated server, graphical client), start gdb in the background and send `SIGTERM` to the *inferior* PID (not gdb's own PID) once you're done observing it — gdb passes the signal through, the process exits, and `bt`/status still get printed cleanly.

### Local test/dev mod directory (`mod/`)

`mod/featureful/` is a local, git-ignored, installed sample-mod gamedir (produced by `cmake --build ... --target install` with `-DGAMEDIR=featureful`) used for manually testing built binaries in a real engine — not a source directory. It contains the built `hl.dll`/`hl.so` and `client.dll`/`client.so` alongside the sample mod's `features/*.cfg`/`*.json`, `templates/*.json`, `maps/`, `models/`, `sound/`, and `sprites/`. It is not tracked by git; treat it as build/test output, not something to edit by hand or commit.

## Running the mod locally (Linux/Xash3D)

Everything under `mod/` is generated/regenerated by the scripts below; nothing in `mod/` is hand-edited or committed (it's git-ignored).

1. **Build the mod's game DLLs** (server/client) and install them into `mod/featureful`:
   ```bash
   ./build-dev.sh
   ```
   This is the quick dev-loop build (see "Build" above for what it wraps). It only produces `hl.so`/`client.so` — it does not build an engine.

2. **Build the Xash3D engine** and install it next to the gamedir, at `mod/` (so `mod/xash3d`, `mod/lib*.so`, and `mod/featureful/` all live side by side, which is Xash3D's expected flat layout):
   ```bash
   ./build-xash.sh
   ```
   This clones `FWGS/xash3d-fwgs` into `./xash3d-fwgs` (git-ignored, first run only), applies any patches from `patches/xash3d/` (see below), builds it 32-bit (matching the mod DLL architecture), and installs it via `./waf install --destdir=mod`. It also (re)generates `mod/run.sh` on every run.
   - `./build-xash.sh clean` — wipe the xash3d-fwgs build dir and reconfigure from scratch.
   - `./build-xash.sh update` — `git pull` + submodule update before rebuilding (picks up upstream engine changes).

3. **Run the mod**:
   ```bash
   mod/run.sh
   ```
   Launches `mod/xash3d -game featureful` with `-dev +developer 2 +sv_cheats 1`. Extra engine args can be passed through, e.g. `mod/run.sh +map boss_demo`.

### Patching the Xash3D engine (`patches/xash3d/`)

If a change to the mod requires modifying the Xash3D engine itself (not this repo's `dlls`/`cl_dll` game code), don't edit the `xash3d-fwgs` checkout directly and expect it to persist — `build-xash.sh` re-clones it if missing and the checkout itself isn't version-controlled by this repo. Instead:

1. Make and test the change inside the `xash3d-fwgs/` checkout.
2. From inside `xash3d-fwgs/`, turn it into a patch: `git diff > ../patches/xash3d/000N-description.patch`.
3. Revert the working tree change in `xash3d-fwgs/` (`git checkout -- <file>`) so the checkout matches upstream again — `build-xash.sh` applies the patch itself on the next run.

`patches/xash3d/*.patch`/`*.diff` are applied (in alphabetical order, so prefix with `000N-` if order matters) right after cloning/updating the engine and before `./waf configure`/`./waf build`. Application is idempotent — a patch already present in the checkout is detected and skipped rather than failing the build. See `patches/xash3d/README.md` for the exact format.

`xash3d-fwgs/` (the engine clone itself) is git-ignored, same as `mod/` and `build*/` — it's fetched by `build-xash.sh`, not committed.

`tools/lib/apply-patches.sh` holds the shared `apply_patches_from <dir>` function both `build-xash.sh` and `tools/build-vhlt.sh` source and call — don't duplicate the apply/skip loop again for a third patch set; add a call to this helper instead.

### Map compiler tools (`tools/`)

`tools/build-vhlt.sh` clones (if missing) and builds [VHLT-V34](https://github.com/twhl-community/VHLT-V34) — the `hlcsg`/`hlbsp`/`hlvis`/`hlrad`/`ripent` map compiler suite needed to compile `.map` sources into `.bsp` for this SDK's maps. It applies patches from `patches/vhlt/` (via `tools/lib/apply-patches.sh`, same idempotent apply-and-skip mechanism as `patches/xash3d/`) right after cloning/updating, before running `make`. It's a plain `make`-based Linux build (`tools/VHLT-V34/src/zhlt-vluzacn/Makefile`), no CMake/waf involved. Outputs land in `tools/VHLT-V34/src/zhlt-vluzacn/bin/`. `./tools/build-vhlt.sh clean` rebuilds from scratch, `./tools/build-vhlt.sh update` pulls upstream first. Like `xash3d-fwgs/`, `tools/VHLT-V34/` is a git-ignored clone, not committed — the actual, persistent modification lives in `patches/vhlt/`.

`patches/vhlt/0001-hlrad-incremental-geometry-checksum.patch` fixes a real gap in `hlrad`'s `-incremental` transfer cache (`hlrad/transfers.cpp`): stock VHLT only invalidates the cached `.inc` file when the *patch count* changes, so a brush move — or an in-place rotation around its own centroid — that happens to keep the same patch count is silently accepted and produces stale bounce lighting on the new geometry, with no warning. The patch adds `GeometryChecksum()` — an FNV-1a hash over every patch's `origin`/`area`/`faceNumber` *and full winding point list* — written into the `.inc` header and re-verified on read; a mismatch now logs `Incremental file [...] is stale (geometry changed), recomputing` and correctly falls back to a full recompute. Regression-tested by `tools/test-hlrad-incremental.sh` (see below), not just by hand.

`tools/test-hlrad-incremental.sh` is the automated regression test for that patch: builds a baseline `.inc` against the bundled synthetic test map (`tools/testdata/ci_test_room.map` — a small, sealed, `NULL`-textured room using only `zhlt.wad`, so it needs no external/copyrighted assets and works on a bare checkout), confirms an unmodified re-run accepts the cache, then flips one byte inside the stored checksum (patch count untouched) and confirms hlrad correctly rejects it as stale and recomputes. Run it after `./tools/build-vhlt.sh` any time `hlrad/transfers.cpp` or the checksum patch changes.

`patches/vhlt/0002-cleanup-freeblock-null-warning-progress-throttle-ub.patch` — three small, independent, low-risk cleanups (no behavior/output change) found from a source review of VHLT-V34 and xash3d-fwgs's BSP-loading code: `common/threads.cpp: GetThreadWork()`'s per-work-item progress `printf` is now gated behind the same percentage-bucket check its own time-estimate print already uses (was unconditional on every dispatched patch/face while holding the global work mutex — the direct cause of multi-MB, mostly-single-line compile logs, e.g. a `full` rebuild of the demo map went from a 1.8MB `hlrad` log to ~12KB for the whole `hlcsg`->`hlbsp`->`hlvis`->`hlrad` chain after this fix); `common/blockmem.cpp: FreeBlock(NULL)` no longer warns (it's a normal no-op, same as `free(NULL)` — was producing ~28,000 spurious log lines per `-incremental` `FailedRead` cleanup pass); `common/bspfile.cpp`'s texinfo byte-swap loop no longer reads 4 floats past the end of `vecs[0]` into `vecs[1]` (undefined behavior, silences a real `-Waggressive-loop-optimizations` warning). See `patches/vhlt/README.md` for the full source-review findings this was drawn from, including what was deliberately *not* changed (global mutable state, manual memory management, `goto`-based cleanup, `MAX_POINTS_ON_WINDING` — all working, load-bearing 20+ year old code where cosmetic modernization risks silent map-corruption bugs for no real benefit).

**Xash3D extended BSP limits — investigated, not implemented:** VHLT-V34 has a dormant `ZHLT_XASH2` build flag (`common/cmdlib.h`, commented out) that writes `BSPVERSION 31`. This does **not** match what this project's actual `xash3d-fwgs` reads — its loader (`engine/common/mod_bmodel.c: Mod_LoadBmodelLumps`) only accepts version 29/30/`QBSP2_VERSION`; version 31 hits the `default:` "wrong version number" error. Current `xash3d-fwgs` instead detects extended clipnode limits via a separate `dextrahdr_t`/`IDEXTRAHEADER` ("XASH" fourcc) lump directory appended after the standard header (`LUMP_BSP30EXT` handling in the same function) — `ZHLT_XASH2` targets an older/different Xash lineage, not this one. Implementing real bsp30ext support would mean writing that extra header/lump table in `hlbsp/writebsp.cpp` and threading 32-bit clipnode support through hlbsp's internals (currently hardcoded to `MAX_MAP_CLIPNODES 32767`) — a substantial, high-risk change to core BSP-writing code. **Don't enable `ZHLT_XASH2`,** and don't invest in real bsp30ext support unless a real map actually hits the 32767-clipnode ceiling (`ZHLT_MAX_MAP_LEAFS` and `ZHLT_LARGERANGE`, both already enabled in `common/cmdlib.h`, already give meaningful headroom — leaf limit 8192→32760 and a larger entity coordinate range — with zero compatibility risk).

`tools/build-maps.sh` compiles every `.map` in `mod/featureful/maps/*.map` (or a single one by name, e.g. `./build-maps.sh featureful_demo`) into a `.bsp` in place, via `hlcsg -> hlbsp -> hlvis -> hlrad`. Three quality modes:
- **`fast`** (default) — `-bounce 0`, which skips hlrad's transfer/vismatrix step entirely, so `-incremental` is deliberately *not* passed here (nothing to cache).
- **`full`** — full vis, extra rad, 8 bounces, `-incremental` on, plus `-customshadowwithbounce -rgbtransfers`: switches hlrad's bounce pass from monochrome-averaged transfers to full RGB transfers (`GatherRGBLight` instead of `GatherLight`), so colored light bounces/bleeds with its own color, and opaque-entity custom shadows are respected during the bounce pass too. Both flags are off by default in stock hlrad; there's no real reason not to have them on outside a quick `fast` preview.
- **`lightonly`** — for iterating on light/entity values only, *without* recompiling geometry: runs `hlcsg -onlyents` (entity-lump-only re-save, skips `hlbsp`/`hlvis` entirely) then `hlrad -incremental`. Requires an existing `.bsp` from a prior `fast`/`full` build of the same map (errors out otherwise) and does **not** pick up brush/geometry edits — re-run `fast` or `full` for those.

It runs with `WADROOT=mod` so `hlcsg` resolves the wad paths baked into each `.map` (recorded from whatever machine authored the map, e.g. `/home/someone/.../Half-Life/valve/halflife.wad`) against `mod/valve/*.wad` instead — VHLT's `hlcsg` retries `$WADROOT/<original-wad's-parent-dir-name>/<wadfile>` when the literal embedded path doesn't exist. It also seeds `mod/valve/zhlt.wad` from `tools/VHLT-V34/tools/zhlt.wad` the first time, since maps expect it alongside the other wads.

**Why `lightonly` matters:** `hlcsg` unconditionally deletes any existing `.inc` on every *normal* run (`common/log.cpp: ResetTmpFiles()`, skipped only for `-onlyents`) — so under `fast`/`full`'s full `hlcsg -> hlbsp -> hlvis -> hlrad` chain, the `.inc` cache never survives to the next `build-maps.sh` invocation anyway, making `-incremental` and the geometry-checksum patch above moot in everyday use. `lightonly` is what actually makes the cache (and the patch) pay off day-to-day.

**All four tools run with `-threads $(nproc)`** in the scripts, on top of `patches/vhlt/0003-posix-auto-detect-thread-count.patch`, which fixes the underlying tool itself: stock `VHLT-V34`'s POSIX `ThreadSetDefault()` (`common/threads.cpp`) always fell back to 1 thread unless `-threads` was passed explicitly — `common/threads.h` hardcoded `DEFAULT_NUMTHREADS 1` for `SYSTEM_POSIX`, so the auto-detect branch in `ThreadSetDefault()` was dead code on Linux, and every `hlcsg`/`hlbsp`/`hlvis`/`hlrad` invocation *outside* this repo's own scripts (e.g. J.A.C.K.'s bundled Build Programs configs, which don't pass `-threads`) silently ran single-core. The patch ports working auto-detection from [`github.com/FreeSlave/vhlt`](https://github.com/FreeSlave/vhlt) (a different personal fork of the same Vluzacn ZHLT v34 base): `sched_getaffinity`/`CPU_COUNT` on Linux, `sysctlbyname` on macOS/BSD, `sysconf(_SC_NPROCESSORS_ONLN)` as the generic fallback — `DEFAULT_NUMTHREADS` is now `-1` for POSIX too, matching what Windows already did via `GetSystemInfo()`. The scripts' explicit `-threads $(nproc)` is now redundant but harmless defense-in-depth. Confirmed by timing: `hlrad -extra -bounce 8` on the demo map went from ~51s single-threaded to ~12s once actually using all 8 cores.

**Lighting quality (`patches/vhlt/0004-double-lightmap-resolution-xash3d.patch`):** doubles lightmap resolution everywhere (8 texels per luxel instead of 16) via a per-texinfo flag bit (`TEX_EXTRA_LIGHTMAP`) that this project's `xash3d-fwgs` already reads independently of the BSP file version — deliberately *not* using VHLT's own dormant `ZHLT_XASH2` flag, which would also bump `BSPVERSION` to `31` and get rejected outright by `Mod_LoadBmodelLumps` (only accepts 29/30/`QBSP2_VERSION`). Unconditional, since this project only targets Xash3D (never classic GoldSource/Software renderer, which the removed 16-texel-step limit existed for). See `patches/vhlt/README.md` for the full derivation.

### CI smoke test for the custom tooling (`manual-tooling-smoke-test.yml`)

`.github/workflows/manual-tooling-smoke-test.yml` (manual `workflow_dispatch` only) builds `build-dev.sh`, `build-xash.sh`, and `tools/build-vhlt.sh` end to end on a clean checkout, then runs `tools/test-hlrad-incremental.sh`. It deliberately does **not** attempt to build or launch the actual `mod/featureful` gamedir — that content (maps, models, sounds, sprites) is private, hand-placed by whoever set up their local `mod/`, not part of this repository, so a fresh checkout has none of it. Keep any future CI-facing tooling checks self-contained the same way `ci_test_room.map` is, rather than assuming `mod/` is populated.

### Known benign warning: "SV_LoadProgs: couldn't get physics API"

Every dedicated-server/engine start under Xash3D logs `Warning: SV_LoadProgs: couldn't get physics API`. This is expected, not a bug: `Server_GetPhysicsInterface()` in `dlls/cbase.cpp` is exported only so the game DLL can detect at runtime whether it's running under Xash3D (`g_fIsXash3D = true`) and fix up a collision-behavior flag (`g_hasCorrectShouldCollide`); it deliberately returns `0` so the engine does *not* actually initialize Xash3D's extended physics API (`engine/server/sv_phys.c: SV_InitPhysicsAPI`), which this classic-GoldSource-style SDK doesn't use. The engine logs the `0` return as a warning regardless of intent — safe to ignore.

### Main menu background maps (Xash3D)

Xash3D FWGS (and stock Half-Life) can show a live 3D map behind the main menu instead of a static image. This is entirely engine/mainui-driven — no client/server DLL code needed, just data:

1. `<gamedir>/scripts/chapterbackgrounds.txt` — one map name per line (no `.bsp` extension); lines that are pure digits are skipped (back-compat with the old numbered list format). `3rdparty/mainui/BaseMenu.cpp: UI_LoadBackgroundMapList()` reads this file on menu init.
2. Each listed map needs a compiled `.bsp` under `<gamedir>/maps/` (build via `tools/build-maps.sh`).
3. On the first menu frame, `UI_StartBackGroundMap()` (`BaseMenu.cpp`) picks one at random and issues `map_background <name>`, which `SV_MapBackground_f` (`engine/server/sv_cmds.c`) loads as a real singleplayer level with `sv_background_freeze` (default on) freezing player physics — no gameplay-side changes required.

For this SDK: `mod/featureful/scripts/chapterbackgrounds.txt` lists background maps (currently the shipped demo maps). Like the rest of `mod/featureful/`'s hand-placed content (`features/*.cfg`, `maps/`, `models/`, etc.), it lives directly in the git-ignored `mod/` gamedir and isn't regenerated by `build-dev.sh`/`build-xash.sh` — it won't survive a from-scratch `mod/` rebuild unless a source copy is added to the repo and wired into the install step.

## Architecture

### Client/server split (classic GoldSource model)
- `dlls/` — server-side game logic (monsters, weapons, entities, game rules). Compiled with `-DSERVER_DLL` into the server game DLL.
- `cl_dll/` — client-side game logic (HUD, view effects, client-side prediction, VGUI). Compiled with `-DCLIENT_DLL` into the client DLL.
- `game_shared/` — code compiled into *both* DLLs (shared entity data, weapon parameter tables, JSON config parsing, damage info, materials, sound scripts, etc.).
- `pm_shared/` — the player movement code, shared between client (prediction) and server (authoritative movement).
- `engine/`, `common/`, `public/` — engine-facing interfaces/headers (`eiface.h`, `cdll_int.h`, etc.) supplied by the engine (GoldSource or Xash3D); these are mostly headers this project doesn't own, defining the ABI boundary.
- `freevgui/` — git submodule, the FWGS VGUI reimplementation used for the client UI on non-GoldSource-compatible platforms.

### Data-driven configuration layer
A large part of "Featureful" behavior is controlled by JSON configs loaded at runtime rather than hardcoded in C++, parsed via `game_shared/json_config.*` / `json_utils.*` and schema helpers (`schema_definitions.*`, `schema_weapons.*`). Examples: weapon templates/parameters (`weapon_templates.*`, `weapon_parameters.*`), sound scripts (`soundscripts.*`), entity templates (`ent_templates.*` in `dlls/`), warpball templates (`warpball.*`), object hints, materials, skill/difficulty data, save titles, followers, inventory. Each of these has a matching doc page under `documentation/content/docs/configuration/`. When changing behavior that's exposed through one of these systems, check the corresponding doc page and keep it in sync, and check `tests/` for an existing `*_test.cpp` covering it — most of these subsystems have dedicated GoogleTest coverage.

### Mod configuration vs. engine configuration
`mod_options.txt` defines compile-time mod options (surfaced as CMake options/`-D` defines). `features/*.cfg` are runtime engine config files (exec'd cfgs for weapons, monsters, HUD layout, ammo, etc.) — don't confuse the two; the former is a build-time toggle list, the latter is data consumed by the running mod.

### Documentation site
`documentation/` is a Hugo site (theme via git submodule `documentation/themes/hugo-book`) published to the project's GitHub Pages. `documentation/content/docs/configuration/` and `entity-guide/` are the primary reference for user/mapper-facing behavior — consult them when a change affects documented behavior, and update them alongside the code.

### CI
`.github/workflows/build.yml` builds client+server for Linux (32-bit, via Steam Runtime schroot) and Windows on every push/PR, then runs the `tests/` GoogleTest suite on Linux only. `manual*.yml` workflows handle on-demand/Android builds; `hugo.yml` deploys the documentation site.
